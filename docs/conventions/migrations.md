# Migration Conventions

We use **Flyway** to manage the schema of the `<default>` (MedSync) datasource.

The `hospital` datasource schema is **not** managed by Flyway — it is owned externally. For local dev / tests, the schema is generated by Hibernate from `@Entity` classes (`drop-and-create`) or loaded from `docker/hospital-initdb/01_schema.sql` (MySQL container).

## Where migrations live

```
src/main/resources/db/
├── migration/         vendor-agnostic SQL (the default — use this whenever possible)
├── vendor_mysql/      MySQL-only SQL (procedures, triggers, JSON columns, SIGNAL …)
└── vendor_h2/         H2-only SQL (rare — empty today)
```

Flyway picks them up automatically because `application.properties` has:

```properties
quarkus.flyway.migrate-at-start=true
quarkus.flyway.locations=db/migration,db/vendor_{vendor}
quarkus.hibernate-orm.database.generation=validate
```

`validate` means Hibernate will **fail to start** if `@Entity` classes don't match the DB schema. The migration is the source of truth.

The `{vendor}` placeholder resolves to the active datasource kind (`mysql` or `h2`). The vendor folder is a **sibling** of `db/migration`, not a sub-folder — Flyway discards sub-locations that overlap their parent. Vendor-specific migrations use the same `V<N>__<description>.sql` naming and live in the same Flyway version stream (V13 might exist in `vendor_mysql/` but not in `vendor_h2/`; that is fine — each database tracks what it applied separately).

## File naming

```
V<N>__<snake_case_description>.sql
```

- `V` prefix, version number, **double underscore**, description, `.sql`.
- Sequential integer versions: V1, V2, V3, ... No gaps.
- Description in snake_case. Short (a few words). Lowercase.

Examples (current state):

```
db/migration/V1__create_patients_table.sql
db/migration/V2__create_users_schema.sql
db/migration/V3__seed_roles.sql
db/migration/V4__add_patient_medico_fk.sql
db/migration/V5__create_paciente_contexto_table.sql
db/migration/V6__create_articulos_cientificos.sql
db/migration/V7__create_medicamentos_schema.sql
db/migration/V8__seed_medicamentos.sql
…
db/migration/V12__add_especialidad_id_and_drop_legacy.sql
db/vendor_mysql/V13__add_database_objects.sql           ← MySQL-only triggers + procedure
```

## Golden rules

1. **Never modify a committed migration.** If you discover a bug in V3, write V9 that corrects it. Modifying V3 changes its checksum and Flyway will refuse to run on any environment that already applied it.

2. **One concern per migration.** A migration that creates a table and seeds data is harder to roll back mentally than two separate files (`V7__create_*` + `V8__seed_*`).

3. **Use MySQL-compatible SQL** that also works on H2 in `MODE=MySQL` whenever possible. Things that work in both:

   - `BINARY(16)`, `VARCHAR(N)`, `TEXT`, `DATE`, `DATETIME`, `TIMESTAMP`, `BOOLEAN`
   - `DEFAULT CURRENT_TIMESTAMP`, `ON UPDATE CURRENT_TIMESTAMP`
   - `PRIMARY KEY`, `UNIQUE`, `FOREIGN KEY`, `CREATE INDEX`

   For features H2 cannot express (stored procedures, multi-statement triggers, `SIGNAL`, MySQL-only `JSON`), put the migration in `db/vendor_mysql/` instead of `db/migration/`. H2 dev and `@QuarkusTest` runs skip it. The application code must continue to work on H2 without those database-side objects — they are server-side enhancements, not load-bearing for the test suite. See [specs/12-05-2026-database-objects/design.md](../specs/12-05-2026-database-objects/design.md) for the first instance of this pattern.

4. **Cross-feature FKs go in a separate migration.** If `patient` references `user.medico_id` but `user` is added later:
   - V1 creates `patients.medico_id` as a scalar `BINARY(16)` **without** a `FOREIGN KEY` constraint.
   - V4 adds the FK once both tables exist.

   This avoids ordering hell and keeps each feature's migration self-contained.

## Standard table template

```sql
CREATE TABLE <table_name> (
    id BINARY(16) NOT NULL,
    -- business columns
    <field_name> <TYPE> [NOT NULL | NULL] [DEFAULT ...],
    -- audit columns (always last)
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    -- constraints
    CONSTRAINT pk_<table_name> PRIMARY KEY (id),
    CONSTRAINT uq_<table_name>_<columns> UNIQUE (<columns>),
    CONSTRAINT fk_<table_name>_<referenced> FOREIGN KEY (<col>) REFERENCES <other_table>(id)
);

CREATE INDEX idx_<table_name>_<columns> ON <table_name> (<columns>);
```

Soft-delete tables add an `activo BOOLEAN NOT NULL DEFAULT TRUE` column and an `idx_<table>_activo` index.

## Seed data migrations

Seed migrations are reserved for **enumerated reference data** the application requires to function (roles, medication statuses, etc.). They are **idempotent** — re-running them on a populated table is a no-op.

Use deterministic UUIDs so seeded rows are referenceable across environments:

```sql
INSERT INTO roles (id, nombre, descripcion) VALUES
    (UNHEX('00000000000010008000000000000001'), 'COO', 'Chief Operating Officer'),
    (UNHEX('00000000000010008000000000000002'), 'DOCTOR', 'Médico tratante'),
    (UNHEX('00000000000010008000000000000003'), 'CMO', 'Chief Medical Officer')
ON DUPLICATE KEY UPDATE descripcion = VALUES(descripcion);
```

Do **not** put user-generated data (test fixtures, demo records) in a Flyway migration. Use a separate dev-profile loader for that.

## Verifying a migration locally

```bash
./mvnw quarkus:dev                                  # H2 in-memory, migrations applied on boot
./mvnw quarkus:dev -Dquarkus.profile=mysql-local    # against docker MySQL
docker compose exec medsync-db mysql -u medsync -p medsync -e "DESCRIBE <table>;"
```

If Flyway fails on boot, the error message lists the failing version and SQL line.

## Common pitfalls

- **Forgetting `NOT NULL DEFAULT TRUE` on `activo`** — soft-deleted tests fail because the column is nullable.
- **Using `DECIMAL(10,2)` without thinking** — fine for currency, wrong for FK columns (use `BINARY(16)`).
- **Mixing camelCase column names** — always snake_case in SQL; the JPA entity maps to it via `@Column(name = "...")`.
- **Adding FK without an index on the FK column** — MySQL creates one automatically, but H2 doesn't. Add `CREATE INDEX idx_<table>_<fk_col>` explicitly to keep the schemas symmetric.
